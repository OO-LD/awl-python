M7 awl.context implementation plan¶

For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

Goal: Build the JSON-LD context that turns an AstDoc into correct RDF, replacing the hand-written static context.

Architecture: A pure function from a set of TypeInfo to a context document. This is the cheapest lever in the whole design: it retargets the entire projection without touching the walker, and it fixes most of the defects measured in the current implementation.

Tech Stack: rdflib and pyld for verification. Every claim below was reproduced locally before being written down.

Contract¶
Consumes a set of TypeInfo
Produces ContextDoc
Depends on awl.contracts

Why this module exists¶

Measured on the current implementation, on the running example: 62 triples with annotate=False, 47 with annotate=True. In the annotated case the collapsed constructor renders as awl:HasArgumentList [ ], an empty blank node: target_voltage=4.2 and c_rate=0.23 are absent from the RDF entirely, because those names are not terms in jsonld_context.py and JSON-LD drops unmapped terms. Statement order is absent in both, because awl:HasPart is unordered.

Most of that is context work, not walker work.

Ordering, at more than one layer¶

@container: @list produces a genuine RDF collection. JSON-LD 1.1 API section 8.3: "List Conversion is the process of taking a list object and transforming it into an RDF collection as defined in RDF Semantics." Verified:

[] a :Method ;
    :body ( [ a :Call ; :callee "charge" ]
            [ a :Call ; :callee "rest" ] ) .

?m awl:body/rdf:rest*/rdf:first ?step retrieves the steps. But it yields members, not positions: recovering an index means counting rdf:rest hops, and SPARQL 1.1's property path grammar has only *, + and ?. Result order is a store artefact, not a guarantee.

So emit both: @container: @list for fidelity, and a materialized integer index as the query surface.

Two mechanisms are ruled out. JSON-LD index maps are defined for "keys that have no semantic meaning, but should be preserved regardless" (syntax spec section 9.9), which disqualifies them by the spec's own framing. SHACL sh:order is non-validating form-layout metadata.

The cross-language numeric hazard¶

JSON-LD 1.1 API section 8.6 warns that lossless numeric round-tripping cannot be guaranteed. This does not currently bite awl-python: both rdflib and pyld preserve 4.0 as xsd:double, because Python's json module parses 4.0 to float and 4 to int.

JavaScript cannot: JSON.parse('4.0') and JSON.parse('4') both yield 4 (verified, Node v25.6.0). So a parameter written target_voltage=4.0 survives a Python round trip and silently becomes an integer through a JavaScript one. The hazard is cross-language, which is exactly the axis the language-agnostic objective cares about.

Mitigation verified: coercing the term fixes the datatype regardless of the native value.

{"@context": {"v": {"@id": "http://ex.org/v", "@type": "xsd:double"}}, "v": 4}

emits "4.0E0"^^xsd:double; without coercion the same input emits "4"^^xsd:integer. Derive the coercion from the field annotations M3 already reads.

Type-scoped disambiguation¶

One term means different things under different node types: args under a method declaration is a parameter list, under a call an argument list; a name under an annotation is a type, elsewhere a variable. Type-scoped contexts express this declaratively and per-type, which is stronger than a qualifier enum, and it is the feature LinkML's generator does not emit.

Non-goals¶

  • Not the embedded per-node context for collapsed types. That is M6.
  • Not RDF emission. That is M8.

"""Build the JSON-LD context that projects an AstDoc to correct RDF."""

from __future__ import annotations

from typing import Any

__all__ = ["AWL", "XSD", "build_context"]

AWL = "https://w3id.org/awl/schema/"
XSD = "http://www.w3.org/2001/XMLSchema#"


def build_context(types: list[dict[str, Any]] | None = None) -> dict[str, Any]:
    """Build the document-level context.

    Parameters
    ----------
    types : list of dict, optional
        ``TypeInfo`` documents. Numeric fields get an explicit xsd:double
        coercion so a float survives a round trip through a JavaScript
        processor.

    Returns
    -------
    dict
        Conforms to ``context-doc.schema.json``.
    """
    context: dict[str, Any] = {
        "awl": AWL,
        "xsd": XSD,
        "@vocab": AWL,
        "_type": "@type",
        # Ordered, so statement sequence survives. Pair with awl:index for
        # querying; rdf:rest*/rdf:first enumerates but does not order.
        "body": {"@id": f"{AWL}body", "@container": "@list"},
        "orelse": {"@id": f"{AWL}orelse", "@container": "@list"},
        "index": {"@id": f"{AWL}index", "@type": "xsd:integer"},
    }
    for info in types or []:
        for field in info.get("fields", []):
            if field.get("pythonType") in ("float",):
                context[field["name"]] = {"@id": f"{AWL}{field['name']}", "@type": "xsd:double"}
    return {"@context": context}

Task 2: The numeric regression¶

  • [ ] Step 1: Write the test
def test_a_float_stays_a_double():
    """Guards the cross-language hazard.

    Python preserves 4.0 as a float, so this passes trivially here. It exists
    because a JavaScript processor cannot: JSON.parse('4.0') === JSON.parse('4').
    Without the explicit coercion the term is emitted as xsd:integer and a
    voltage silently changes type.
    """
    types = [{"identity": {"iri": "ex:C", "scheme": "py"}, "fields": [
        {"name": "target_voltage", "isLink": False, "isMany": False,
         "declarationForm": "plain", "pythonType": "float"}]}]
    context = build_context(types)["@context"]
    assert context["target_voltage"]["@type"] == "xsd:double"


def test_the_coercion_survives_an_integer_valued_input():
    from pyld import jsonld

    context = build_context([{"identity": {"iri": "ex:C", "scheme": "py"}, "fields": [
        {"name": "v", "isLink": False, "isMany": False, "declarationForm": "plain",
         "pythonType": "float"}]}])["@context"]
    nquads = jsonld.to_rdf({"@context": context, "v": 4}, {"format": "application/n-quads"})
    assert "double" in nquads, nquads

def test_an_unmapped_term_still_produces_a_triple():
    """The defect measured in the current implementation: unmapped terms vanish.

    A fallback @vocab is what prevents it.
    """
    doc = {"@context": build_context()["@context"], "_type": "Call", "invented_field": 1}
    graph = Graph()
    graph.parse(data=json.dumps(doc), format="json-ld")
    assert any("invented_field" in str(p) for _, p, _ in graph)

    contracts.validate(build_context(), "context-doc")

Known limits¶

  • pythonType is not in type-info.schema.json yet. Either add it there, which is a contract change affecting M3, or derive the coercion in M8 from the annotation instead. Decide before implementing, and if the contract changes, say so loudly: every module reading TypeInfo is affected.
  • Type-scoped disambiguation for args and Name is described above but not implemented in the sketch. Add it once M5 emits nodes that need it.
