Deriving semantic graph from code: principles, prior art, and design for AWL-LD¶

Scope¶

AWL derives an RDF graph from an abstract syntax tree. The open design problem is redundancy and cutoff level: which detail becomes graph, and what makes the result compact enough to query.

This document asks which principles and tooling from comparable projects are sound, which AWL should reuse rather than rebuild, and where AWL's own objectives make a different answer correct. It is an analysis, not an implementation plan.

Positions taken as given:

  • The vocabulary must be language-agnostic. Building the graph from other languages' ASTs is future work, but the constraint shapes the design now.
  • Identity is import-path based, rename-safe, re-export-safe, optionally versioned.
  • OO-LD LinkedBaseModel is mid-migration, so the mechanism analysed is plain dataclasses carrying schema-derived annotations.
  • The JSON-LD context is a first-class lever, on equal footing with AST processing.

Claims marked verified were reproduced locally or read from a primary source. Claims marked reported come from secondary sources. Claims marked reconstructed are derived from a project's documented schema rather than from running the tool.

Naming¶

AWL-LD is the primary name; AWL is used as shorthand in this document. The bare acronym has one hard collision and one soft one.

AWL = Anweisungsliste, the German name for the IEC 61131-3 Instruction List language, implemented in Siemens STEP 7 as the native statement list for S7-300, S7-400 and S7-1500. .AWL is a real source-file extension for PLC code. That is the same industrial and laboratory automation domain AWL-LD targets: battery cyclers and tensile test rigs are PLC-controlled, and in German-speaking industry "AWL" already names a programming language.

The soft collision is the *WL family. CWL and WDL are hand-authored dataflow languages. AWL-LD is derived from code and is control-flow. Both connotations mislead. It is also not a language in the sense CWL is; Joern calls its equivalent "a language-agnostic intermediate graph representation", which is the honest category.

Renaming outright would cost w3id.org/awl/schema/, the PyPI name, the repositories and a Zenodo DOI. Leading with AWL-LD is sufficient: no PLC context claims it, and the README already uses it.

Worked examples¶

Two, used throughout. The first is minimal, the second is real.

Example A: control flow and literal arguments¶

# battery/params.py
from dataclasses import dataclass

@dataclass
class ChargeParam:
    target_voltage: float
    c_rate: float

# procedure.py
from battery.params import ChargeParam
from battery.device import charge, rest

def procedure(cycles: int) -> None:
    i = 0
    while i < cycles:
        charge(ChargeParam(target_voltage=4.2, c_rate=0.23))
        rest(600)
        i += 1

Example B: typed quantities and opaque numerics¶

Abridged from opensemantic.characteristics.quantitative-python/examples/tensile_test.py.

class TensileTestSpecimen(OswBaseModel):
    length: Length
    width: Width
    thickness: Length
    cross_section_area: Optional[Area] = None
    e_mod: Optional[ModulusOfElasticity] = None

def tensile_test_analysis(dataset: TensileTestDataset) -> TensileTestDataset:
    if dataset.specimen.cross_section_area is None:
        dataset.specimen.cross_section_area = (
            dataset.specimen.width * dataset.specimen.thickness
        )
    df = dataset.result.to_df()
    df["strain"] = df["elongation"] / dataset.specimen.length.to_pint()
    df["stress"] = df["force"] / dataset.specimen.cross_section_area.to_pint()
    linear = df[df["strain"] <= dataset.result.linear_region.to_pint()]
    slope, *_ = linregress(
        linear["strain"].pint.to_base_units().pint.magnitude,
        linear["stress"].pint.to_base_units().pint.magnitude,
    )
    slope = (slope
             * linear["stress"].pint.to_base_units().pint.units
             / linear["strain"].pint.to_base_units().pint.units)
    dataset.specimen.e_mod = ModulusOfElasticity.from_pint(slope.to("Pa"))
    dataset.result = TensileTestResult.from_df(df)
    return dataset

Example B is the hard case and the honest test of every claim below. It mixes fully typed OO-LD quantities with an opaque third-party numerical call, and it strips units immediately before that call.

Part I: Problem and prior art¶

1. Two theories of code graph¶

Code-indexing tools answer "what is in this repository and how does it connect", for someone navigating unfamiliar code. AWL answers "what does this procedure do, in what order, with what values, and what do those values mean", for a machine reasoning over a workflow.

That difference sets the cutoff. Graphify's Python configuration (graphify/extract.py:767, verified) admits four node families:

class_types=frozenset({"class_definition"}),
function_types=frozenset({"function_definition"}),
import_types=frozenset({"import_statement", "import_from_statement"}),
call_types=frozenset({"call"}),
function_boundary_types=frozenset({"function_definition"}),

Bodies are walked only to collect calls. Statement order, control flow and literal argument values are discarded. Those are what AWL exists to carry.

So the cutoff level of the indexing tools is not transferable. Their principles, tooling, and in several cases their actual output are, and that is what follows.

2. Prior art¶

2.1 Nobody ships full-AST RDF graph¶

Kythe's schema has node kinds for record, function, variable, tapp and anchor, and none for statements, expressions, operators or literals. Glean states the position outright: "while the full AST could be stored, for efficiency only the needed parts are kept, usually locations of definitions and cross-references, but not expressions" (reported). SCIP models only occurrences of symbols in ranges. CodeOntology, the closest direct precedent, made statement and expression triples an opt-in flag, default off.

The two systems that do keep the full AST, CodeQL and Joern's Code Property Graph, are a relational database and a property graph. Neither is RDF.

AWL is deliberately going where others declined. That makes the collapse mechanism not an optimisation but the thing that makes the design viable.

2.2 Tiny node vocabulary beats class per syntax form¶

Joern's CPG has no ASSIGNMENT, BINARY_OP or FIELD_ACCESS node. x = y + 1 is a CALL named <operator>.assignment whose second argument is a CALL named <operator>.addition. CodeQL does the relational equivalent: one exprs table keyed (id, kind, parent, idx).

CodeOntology took the opposite route, minting an OWL class per AST construct. Its Java parser was last pushed 2018-06-27 with 2 stars; a Python port, SandroGT/CodeOntologyPython, 2023-03-26 with 1 star (both verified). Joern was last pushed 2026-08-18 with 3430 stars (verified).

Do not mint an RDF class per Python ast node type. It would version AWL against CPython's grammar forever and defeat the language-agnostic objective.

2.3 Two orderings, not one¶

Verified against the CPG specification:

  • ORDER is syntactic: "This integer indicates the position of the node among its siblings in the AST. The left-most child has an order of 0."
  • ARGUMENT_INDEX is semantic: "AST-children of CALL nodes have an argument index, that is used to match call-site arguments with callee parameters", numbered 1 to N, with "index 0 reserved for implicit self / this parameter". Named arguments set it to -1 and carry ARGUMENT_NAME; "if the PARAMETER_NAME field is set, then the ARGUMENT_INDEX field is ignored".

Conflating position-in-body with argument-binding-position hurts exactly at AWL's collapse boundary, where a call's keywords become a class's named properties.

2.4 Ordering mechanisms to avoid¶

JSON-LD index maps are defined for "keys that have no semantic meaning, but should be preserved regardless" (JSON-LD 1.1 syntax, section 9.9, verified). Statement order is semantically meaningful, so @container: @index is disqualified by the specification's own framing.

SHACL sh:order sits in the "Non-validating property shape characteristics" section and is intended for form building. A conforming processor never emits a result for it.

2.5 No workflow ontology models control flow¶

CWL has no step order at all: "An implementation may choose to execute the steps in a different order than listed". Ordering is derived entirely from source and outputSource data links. P-Plan expresses order only through p-plan:isPreceededBy, transitive and index-free. Surveys report the same gap in OPMW, wfdesc and ProvONE, attributed to dataflow-driven scientific-workflow origins (reported).

AWL's If, While and For have no existing RDF vocabulary to reuse. That is a contribution area and a warning: the ecosystem concluded ordered imperative statements are the wrong abstraction for a workflow plan.

2.6 FnO is the precedent for callee-defined predicates¶

In the Function Ontology, an fno:Parameter declares fno:predicate, the RDF property to use when binding its value. A call is an fno:Execution with fno:executes plus plain triples using those declared predicates.

That is "the callee's own description defines the predicates of the call node". AWL reaches the same target through a type-scoped JSON-LD context. FnOio/fno-descriptor-python already derives FnO from Python type hints, last pushed 2022-08-10 with 2 stars (verified). Align with the vocabulary; do not depend on it.

2.7 Stack graphs is archived¶

github/stack-graphs is archived, last pushed 2025-09-09 (verified). Take the architecture, not the crate, and do not build an equivalent. AWL resolves call targets within one document plus its declared imports.

2.8 The pyiron and NFDI stack: PWD, semantikon, flowrep¶

The closest active work, from an adjacent community. Three packages that reach a workflow knowledge graph without touching an AST.

Python Workflow Definition (pythonworkflow/python-workflow-definition, last pushed 2026-08-17, published in Digital Discovery 2025, verified). A workflow is a Python module, a JSON graph, and a conda environment file:

{
  "nodes": [
    {"id": 0, "type": "function", "value": "workflow.get_prod_and_div"},
    {"id": 2, "type": "input", "value": 1, "name": "x"}
  ],
  "edges": [{"target": 0, "targetPort": "x", "source": 2, "sourcePort": null}]
}
  • Identity is the dotted import path. AWL's chosen scheme is already in production in a sibling project.
  • Version drift is handled by shipping a conda environment file, not by versioning identifiers. A real alternative to a SCIP-style version component, better suited to scientific workflows where the whole environment matters. The cost: the identifier is no longer self-describing.
  • Cutoff is pure dataflow. No statements, no control flow, no literals except as input nodes. Independently confirms 2.5.

semantikon (pyiron/semantikon, last pushed 2026-08-19, verified). Scientific context on functions through type annotations, emitted as an rdflib graph:

def get_speed(
    distance: u(float, uri=EX.distance, units="meter"),
    time:     u(float, uri=EX.time,     units="second"),
) -> u(float, uri=EX.speed, units="meter/second"):
    return distance / time

Targets PMDco on BFO and OBI, plus QUDT for units, and validates units at runtime through pint. flowrep (pyiron/flowrep, last pushed 2026-08-17) supplies the exchange format semantikon.get_knowledge_graph reads.

Comparison, and where AWL actually differs:

semantikon stack AWL
Input Decorated functions plus exported dataflow graph Source AST
Semantics attached to Parameters, via u(...) in each signature Resolved type, via schema-derived context
Who writes the IRIs The developer, in every annotated signature Nobody; generated from the schema
Control flow None Yes
Round-trip to source No Yes
Partial annotation All or nothing per function Degrades continuously

The differentiator is progressive enhancement, not coverage. semantikon produces a better graph than AWL for a fully annotated function, and it should be preferred there. What it cannot do is produce anything for a function whose author declined to annotate it, and it requires the author to write RDF vocabulary in the signature of every function they touch.

AWL's position is a gradient with no cliff: plain code yields a call graph, partially typed code yields typed boundaries where types exist, fully typed code yields the collapse. Section 8 makes this precise, and section 9 shows how the untyped end is raised without asking developers to write IRIs.

One point of honesty about "no leaking". OO-LD's generated models carry the context in model_config, so RDF vocabulary is present in Python source either way. The real distinction is that OO-LD's copy is machine-generated and never hand-maintained, and that call sites are RDF-free: a developer writes ChargeParam(target_voltage=4.2) and never types an IRI. semantikon's annotations sit in the signatures developers write. That is the claim worth making.

3. What existing tools already give, and where reuse stops¶

Applied to example B. Reconstructed from each tool's documented schema.

Construct Graphify SCIP Kythe
class TensileTestSpecimen fields and their types -[references, field]-> Length, Width, Area, ModulusOfElasticity ...tensile_test/TensileTestSpecimen#e_mod. variable node, typed edge to tapp
def tensile_test_analysis(ds: TensileTestDataset) -> TensileTestDataset -[references, parameter_type]->, -[references, return_type]-> (). descriptor plus occurrences function node, signature via fn#builtin
class TensileTestResult(TabularData) -[inherits]-> Relationship.is_implementation extends
cross_section_area = width * thickness nothing nothing nothing

Optional is filtered as a typing container and float as annotation noise; ModulusOfElasticity survives.

Reuse them for the type skeleton. They are sufficient there and should not be rebuilt. Every class, every field, every field's declared type, parameter and return types, inheritance.

All three lack the same thing: intra-procedural dataflow. Kythe's ref/writes records that e_mod was written; nothing connects it to the reads that produced the value. Navigation does not need that edge, so none of them emit it.

Also lost by all three: the literal arguments. Length(value=100, unit=LengthUnit.milli_meter) reduces to a calls edge, discarding 100 and milli_meter. For a materials knowledge graph that is the payload.

The reuse split¶

Layer Supplier
Identity, declarations, field types, inheritance SCIP for versioned symbols, or Graphify
Intra-procedural dataflow Joern CPG REACHING_DEF edges, or python-graphs for a pure-Python CFG and DFG
Typed-boundary provenance AWL
Literal arguments, control flow, collapse AWL only

This is the concrete answer to "can we just reuse their output". For the first two rows, yes. The last two are unbuilt anywhere.

Part II: Principles¶

4. Graphify's principles, and the tooling embodying each¶

Observation before inference _SymbolResolutionFacts, resolved in a later pass Extraction never guesses; guessing becomes auditable

Quoted rationales are the authors' own comments in graphify/ids.py and graphify/extractors/base.py.

5. AWL's own principles¶

  1. Language-agnostic serialization, now binding rather than aspirational.
  2. The AST is the document, and it round-trips to source.
  3. Semantics live in the context, not the extractor. One document, many RDF projections.
  4. Restriction is a goal. JSON Schema constrains which constructs and which calls are legal in a workflow domain.
  5. Types carry their own semantics. The resolved type defines meaning, and the developer never writes an IRI.

Principles 1, 3 and 5 have no counterpart in the indexing tools. Principle 2 is unusual across the entire field.

6. Compatibility and tensions¶

Graphify principle Verdict Note
Cutoff as declaration Adopt, extended AWL needs transparent and opaque type sets, plus a content-dependent condition: a call collapses if and only if its callee resolves to an annotated type
One normalization authority Adopt wholesale More critical for AWL, whose identifiers are global IRIs, so a collision is a wrong assertion rather than a merged node
Observation before inference Adopt wholesale The enabling change; nothing else works without it
Provenance in the data model Adopt, different tooling See tension 2
Ambient versus corpus vocabulary Adopt, inverted contents See tension 3
Small closed relation vocabulary Adopt, corroborated by 2.2 AWL has better tooling for it: type-scoped contexts
Stages as total functions Adopt wholesale Purely architectural
Deterministic by default Adopt with care Section 9 introduces a probabilistic path; it must stay quarantined

Tension 1: round-trip versus cutoff¶

If the AST is the document, eliding nodes breaks unparse. The backparsable flag in src/awl/core.py is this tension left unresolved as a boolean.

Resolution: stop treating document and graph as one artefact. Keep the document complete, put the cutoff in the projection. RDF canonicalization normalizes layout away by design, so the RDF projection is explicitly lossy in reverse. That is coherent, and it is SCIP's transmission-versus-storage split, but it must be stated rather than assumed.

Tension 2: provenance in RDF¶

A triple carries no attributes.

Option Strength Cost
Named graphs Clean, standard, queryable per graph Needs quads; to_jsonld() emits one document today
RDF-star Most expressive Uneven tool support
Parallel inferred graph Simplest One bit only

Named graphs are recommended. Section 9 raises the stakes: once meaning can be retrofitted by a model, declared and inferred semantics must never be indistinguishable.

Tension 3: ambient vocabulary is domain-relative¶

Graphify lists dataclass in _PYTHON_DECORATOR_NOISE as "ambient vocabulary, not corpus symbols". For AWL it is the primary identity signal. The principle transfers, the contents invert. Adopting the lists verbatim would be worse than having none.

Part III: Design¶

7. Language-agnostic vocabulary, with CPG as blueprint¶

Correction worth stating first: tree-sitter does not normalize across languages. It is many parsers with different node vocabularies (function_definition in Python, function_declaration in JS, method_definition in TS). Graphify's LanguageConfig is a thin normalization layer mapping those names onto four roles. The normalization AWL wants is CPG's.

Joern's Code Property Graph is explicitly "a language-agnostic intermediate graph representation of code designed for code querying", one layered schema across all frontends. Six mechanisms transfer.

  1. Neutral core vocabulary. METHOD, BLOCK, CALL, CONTROL_STRUCTURE, IDENTIFIER, LITERAL, LOCAL, RETURN, TYPE_DECL, TYPE, MEMBER. Close to exactly what AWL's workflow profile needs, and none of it Python-specific.
  2. Terminology neutrality. Procedures, functions and methods are all METHOD. BLOCK rather than "compound statement", because blocks yield values in some languages.
  3. One node type plus discriminator. CONTROL_STRUCTURE carries a type property rather than spawning If, While, For classes.
  4. Escape hatch. UNKNOWN covers "any AST node that the frontend would like to include in the AST but for which no suitable AST node is specified".
  5. Raw frontend labels as properties, not types. PARSER_TYPE_NAME stores the "AST node type name emitted by parser", explicitly not used for control-flow construction.
  6. Declared language-specific dimensions. A LANGUAGE property names the frontend; SIGNATURE has no strict format "so it can be chosen by the frontend implementor to fit the source language"; for FULL_NAME, "the details of what constitutes a fully-qualified name are language specific".

This resolves tension 1¶

Mechanisms 4 and 5 let AWL keep a language-neutral vocabulary and round-trip Python exactly, because the Python-specific label rides as a property while the node type stays neutral. Vocabulary choice and frontend choice become independent, so principle 1 does not force a move to tree-sitter.

Joern as second frontend, not a replacement¶

pysrc2cpg already emits the neutral vocabulary plus REACHING_DEF dataflow, which is the gap identified in section 3. Roughly the whole workflow profile, for free.

Caveats: Joern is JVM and Scala, heavy for a Python library, and CPG does not round-trip to source. So do not replace AWL's frontend with it. Two frontends, one vocabulary: Python ast for round-trip fidelity, exported CPG for breadth and dataflow.

Sanity check against non-Python source¶

function procedure(cycles: number): void {
  let i = 0;
  while (i < cycles) { charge(new ChargeParam(4.2, 0.23)); rest(600); i += 1; }
}
Python ast TypeScript Neutral vocabulary
FunctionDef function_declaration METHOD
body list statement_block BLOCK
Assign lexical_declaration CALL <operator>.assignment
While while_statement CONTROL_STRUCTURE type While
Call call_expression CALL
Call ClassName(...) new_expression CALL, collapsed
AugAssign augmented_assignment_expression CALL <operator>.assignmentPlus
arg cycles: int required_parameter METHOD_PARAMETER_IN plus TYPE

Two findings. Call and new_expression are distinct in their grammars and identical semantically, which is mechanism 3 earning its keep. And Python keyword arguments have no TypeScript equivalent, so the collapse's input shape differs by language while its output does not. The collapse must therefore be defined over the resolved callee's parameter names, not over the source's keyword syntax. That is why 2.3's ARGUMENT_INDEX and ARGUMENT_NAME split matters.

8. Identity¶

Base scheme¶

  1. Detect the definition: a ClassDef carrying @dataclass or an OO-LD base.
  2. Mint from the fully qualified name under a configurable module-to-namespace mapping. Adopt Kythe's vnames.json pattern: identity minting is declarative configuration mapping path patterns to identity fields, not code.
  3. Carry a language or scheme dimension, per Kythe's VName language and SCIP's scheme.
  4. Carry an optional version component, per SCIP, or pin the environment instead, per PWD (2.8). Choose deliberately; do not do both. An FQN identifies a name, not a contract.
  5. Derive properties from the class body's annotated assignments.
  6. Resolve call sites through import facts. Do not write the resolver: Scalpel's FQN Inferrer and PyCG exist. Scalpel was last pushed 2024-03-28 (verified).

Failure modes¶

Mode Solved by Action
Re-exports Kythe emits both aliases and aliases/root Emit the alias hop and the resolved-to-root target so queries pick their indirection level. The likeliest source of duplicate nodes in Python
Aliases Local import table Straightforward
Overloads SCIP method-disambiguator Required, see below
Version drift SCIP version component or PWD environment file Point 4
Star imports Nothing, anywhere Make import * illegal in the domain schema. This is what the restriction objective is for

Identity is the typed instantiation, not the function¶

The important refinement, and the mechanism that makes example B tractable.

scipy.stats.linregress is generic linear regression. Attaching (LinearStrain, Stress) -> ModulusOfElasticity to that identifier asserts it globally, so every other use of linregress inherits it. The semantics belong not to the function but to its typed instantiation:

scipy.stats.linregress                        no semantics, ever
scipy.stats.linregress(LinearStrain, Stress)  -> ModulusOfElasticity

This is functools.singledispatch semantics, and it is what SCIP's method-disambiguator and Kythe's opaque signature field exist for.

The payoff is large. With OO-LD types on the arguments, the typed instantiation is derivable statically at every call site. A model is needed once, to propose the mapping; dispatch afterwards is deterministic.

Retroactive minting. Kythe's entry store is append-only facts keyed by VName, so any analyzer may add facts about a symbol later and they join everywhere it was referenced. AWL should adopt the same property: mint the identifier for an opaque callee now, attach semantics whenever they become known, and every prior reference gains meaning without reprocessing. This is the architectural reason identity must be stable and global before anything else is built.

Dimensional analysis validates a proposed instantiation for free. Strain is dimensionless, so Stress / LinearStrain has dimension Pa, consistent with ModulusOfElasticity. Any proposed signature failing the dimensional check is rejected without executing anything. Deterministic, cheap, and it catches a large error class before section 9's expensive machinery runs.

Two complications visible in example B:

Arity. slope, *_ = linregress(...) discards four values; linregress returns five. The annotation target is a result schema, not a return type: .slope : ModulusOfElasticity, .rvalue : CorrelationCoefficient. More work, more reusable, and a natural fit for OO-LD.

The units are stripped before the call. The arguments are linear["strain"].pint.to_base_units().pint.magnitude, that is, dimensionless float arrays. (LinearStrain, Stress) describes values three attribute accesses upstream. The typed boundary is not at the call site, and AWL must trace back through a third-party wrapper chain to recover it. This is the hardest concrete case in the example and it should be treated as the acceptance test for any implementation.

9. What AWL actually extracts, and how far down¶

Typed boundaries, not operation semantics¶

dataset.specimen.e_mod = ModulusOfElasticity.from_pint(slope.to("Pa"))

Whatever opaque computation produced slope, at the moment it is assigned to a typed member it acquires meaning. The same holds in reverse when a typed member is read out of an input argument. Typed members form a lattice of crossings: computation between crossings is opaque, meaning is recovered at every crossing, and there are many crossings per function rather than one per signature.

That is strictly more than signature-level annotation, and it is the precise sense in which AWL sees "inside" a function.

State the limit honestly. What is recovered is typed-boundary provenance: e_mod depends on width, thickness, length, force, elongation. The operation is not recovered. "Linear regression over the elastic region" is unavailable unless the callee's typed instantiation is known (section 8) or a model reads the code (below).

One genuine exception, and it is worth building on: width * thickness where both operands are typed quantities has a dimensionally derivable result type. That is real operation semantics, statically decidable, and unmatched by any project surveyed.

Claim Delivered
Semantics of arbitrary operations No
Typed-boundary provenance at many points per function Yes
Result type of arithmetic over typed quantities Yes, by dimensional analysis
Meaning of third-party numerics Only via a registered typed instantiation

Retrofitting meaning onto untyped code¶

The untyped end of the gradient. Plain or partially typed code yields hints; a model can propose meaning; the extraction is expensive, so it must be persisted against a global target and shared across repositories rather than recomputed per consumer.

OO-LD is a good target for a reason that is easy to miss: because the model's task is not "choose a vocabulary" (open-ended, unverifiable) but "choose a profile schema from a registry" (closed, validatable, recorded as a versioned $id). The output is a schema URL plus an instance, and both are checkable.

Validation, cheapest first:

Stage Cost Catches
Dimensional analysis of the proposed signature Free, deterministic Large class of wrong types
Schema validation of instances Cheap Structural errors
Execution against literature reference data Expensive Wrong labels, semantically
Cross-repository agreement on the same schema Ongoing Idiosyncratic mappings

Literature cross-validation is the strong step and deserves emphasis. Extract input and reported output from published work (a tensile test with attached plot or CSV and a reported E-modulus), run the schema-wrapped function, compare, repeat across independent sources. Unlike unit tests, the error sources are uncorrelated, so this validates the label, not merely the arithmetic.

Three limits to record:

  • Coverage is uneven. Only reported quantities get signal. cross_section_area and the 0.2 percent linear_region cutoff appear in no results table, so intermediates stay unvalidated. Confidence is high at the outputs and absent in the middle, which is where a retrofit is riskiest.
  • Convergence is on convention. If the field uses a 0.2 percent offset convention, cross-validation confirms the convention. That is the right outcome for interoperability and it makes the validated semantics explicitly community-relative.
  • The corpus is the asset. Paper-to-(input, reported output) pairs are expensive to assemble and outlast any pipeline built on them. Treat as a deliverable.

Retrofitted meaning must be distinguishable from declared meaning, permanently. This is where tension 2 stops being a nicety. Note also that a retrofit has no instance document to pin a versioned schema $id: the mapping lives in a generated annotation or a sidecar, so it needs its own version pin and provenance tier, or a temporary fallback vocabulary becomes indistinguishable from a consensus one once it propagates.

Why multiple vocabularies is a feature¶

A single global vocabulary is not achievable and not required. OO-LD carries a consensus mapping in the context while community synonyms ride along as structured annotations, so the consumer selects a mapping set rather than the producer enforcing one. That also accommodates a lazy or temporary vocabulary for freshly retrofitted code, upgraded later without rewriting instances. "One syntax, tiered semantics" is the correct answer to the global-target objection, subject to the version-pin caveat above.

11. The context lever¶

What AWL has and the indexing tools structurally lack. All claims here were reproduced locally against rdflib and pyld.

Ordering, at more than one layer¶

@container: @list produces a genuine RDF collection. JSON-LD 1.1 API section 8.3: "List Conversion is the process of taking a list object and transforming it into an RDF collection as defined in RDF Semantics."

[] a :Method ;
    :body ( [ a :Call ; :callee "charge" ]
            [ a :Call ; :callee "rest" ]
            [ a :Call ; :callee "increment" ] ) .

?m awl:body/rdf:rest*/rdf:first ?step retrieves all three (verified). But it yields members, not positions: recovering an index means counting rdf:rest hops, and SPARQL 1.1's property path grammar has only *, + and ?. Result order is a store artefact, not a guarantee.

Emit both: @container: @list for fidelity, since it costs nothing and round-trips, and a materialized integer index as the query surface. Optionally derive p-plan:isPreceededBy in the plan projection. Keep 2.3's two orderings separate.

Numeric round-trip, and where it actually bites¶

JSON-LD 1.1 API section 8.6 warns that "when JSON-native numbers are deserialized to RDF, lossless data round-tripping cannot be guaranteed", and that an xsd:double of 2.0 "will result in an xsd:integer with a value of 2 in canonical lexical form when converted from RDF to JSON-LD and back to RDF".

This does not currently bite awl-python. Both rdflib and pyld preserve 4.0 as xsd:double (verified), because Python's json module parses 4.0 to float and 4 to int.

JavaScript cannot: JSON.parse('4.0') and JSON.parse('4') both yield 4, and Number.isInteger is true for both (verified, Node v25.6.0). A JavaScript processor must emit xsd:integer.

So the hazard is cross-language, exactly the axis principle 1 cares about. A parameter written target_voltage=4.0 survives a Python round-trip and silently becomes an integer through a JavaScript one. Precision loss is real in both: 1.234567890123456789 returns as 1.234567890123457 (verified), the canonical form rounding the mantissa to 15 digits.

Mitigation verified: coercing the term fixes the datatype regardless of native value.

{"@context": {"v": {"@id": "http://ex.org/v", "@type": "xsd:double"}}, "v": 4}

emits "4.0E0"^^xsd:double; without coercion the same input emits "4"^^xsd:integer.

Type numeric terms explicitly, derived from the field annotations AWL already reads. And state plainly that the authoritative round-trip is document to source, never RDF to source.

Term rescue via embedded context¶

A fallback @vocab makes unmapped keys expand rather than drop. For a collapsed type the namespace is unknown when the context is authored, so post-processing emits an embedded @context on that node object. JSON-LD 1.1 permits a context at any node object. Verified:

[] a :Call ;
    :callee <https://w3id.org/awl/py/battery.device.charge> ;
    :hasArgument [ a <https://w3id.org/awl/py/battery.params.ChargeParam> ;
            ns1:c_rate 2.3e-01 ;
            ns1:target_voltage 4.2e+00 ] .

with ns1 bound to the type's namespace. This is what makes the collapse lossless.

Disambiguation via type-scoped contexts¶

One term meaning different things under different node types: args under a method declaration is a parameter list, under a call an argument list; a name under an annotation is a type, elsewhere a variable. This is AWL's answer to the closed-vocabulary principle and stronger than a qualifier enum, because disambiguation is declarative and per-type. It is also the feature LinkML's generator does not emit, and therefore OO-LD's clearest differentiator.

12. Alignment targets¶

  • FnO for call semantics: fno:Execution, fno:executes, per-parameter fno:predicate, at minimum as owl:equivalentProperty mappings. Language-neutral, which principle 1 requires.
  • P-Plan for the plan layer, PROV-O for the trace layer. AWL's TBox and ABox union is P-Plan's structure already.
  • PROV-O derivation for the section 9 provenance edges specifically, since typed-boundary provenance is prov:wasDerivedFrom at sub-function granularity.
  • CPG's schema for the neutral node vocabulary, per section 7.
  • PMDco, BFO, OBI and QUDT if AWL targets materials science; semantikon has validated these choices in that domain. QUDT covers units, which example B needs and the AWL vocabulary does not address. Not exclusive with FnO: FnO covers the call, PMDco the quantities.
  • RO-Crate conformsTo for declaring which restriction profile a document claims, and Workflow Run RO-Crate's Provenance Run Crate for packaging execution traces (section 14).
  • Glean's codemarkup pattern: define the workflow projection as derived rules (SPARQL CONSTRUCT or SHACL) over language-specific base facts. This is also how a second frontend stays cheap.
  • JSON Schema versus SHACL: do not duplicate. Document-shaped constraints to JSON Schema as an authoring-time gate; path-shaped-across-the-graph to SHACL.

Profiles over one pipeline, replacing the backparsable boolean.

Part IV: Execution tracing¶

Everything above concerns the static plan. This part concerns instantiation: what actually ran, along which path, with which values.

14. Plan and trace¶

The scientific workflow community already has the vocabulary:

Term Status in AWL-LD
The recipe prospective provenance Parts I to III
The run retrospective provenance This part

Bridge: p-plan:Activity with p-plan:correspondsToStep, plus prov:used and prov:generated.

The observation that reconciles AWL-LD's control flow with the dataflow ecosystem: a trace is always a DAG, even when the plan contains loops and branches. A loop of N iterations becomes N activities; a branch resolves to exactly one path. So control flow lives in the plan, and the trace is the unrolled dataflow DAG that CWL, PROV, P-Plan and PWD already model. AWL-LD sits upstream of those vocabularies rather than competing with them, which removes the apparent conflict noted in 2.5.

Two things a trace needs that PROV does not supply: a stable identity per plan step (section 8, again) and an iteration ordinal. PROV has no loop counter.

For packaging a run, Workflow Run RO-Crate provides three nested profiles under w3id.org/ro/wfrun/:

Profile Records
Process Run Crate Tool executions as CreateAction, implicit workflow
Workflow Run Crate Adds a ComputationalWorkflow instrument and FormalParameter slots. Individual step executions are not represented
Provenance Run Crate Adds per-step CreateAction entities and intermediate outputs

Provenance Run Crate is the target. It reuses the conformsTo convention already recommended in section 12.

The decisive finding: AiiDA has real control flow but keeps it out of its provenance graph. Its documentation states the branch and iteration logic itself is not a node; provenance captures the data and processes actually created. So "which branch was taken" is first-class nowhere.

16. The existing trace draft, assessed¶

The awl-schema README already contains a tracing draft: sys.settrace events serialized as a steps list, each entry carrying func, lineno, locals, os, timestamp and type, with a code back-reference of the form {_type, lineno}.

It is conceptually ahead of the field.

Feature Note
steps with @container: @list Already the ordering choice recommended in section 11
Branch resolution The If appears as a line event and subsequent events reveal the taken path
Loop iterations The While recurs with changed locals. Nothing else in the survey records this
code: {_type, lineno} Independently reinvents p-plan:correspondsToStep
Variable-level state locals at every line event is finer than any WMS; AiiDA and CWL capture step inputs and outputs only
Environment declared out of scope Correct, and it matches how WRROC separates buildInstructions from the run

Seven gaps.

  1. lineno is a fragile join key. Edit the file and every historical trace orphans. Kythe's design is instructive: the anchor is deliberately the volatile part and the VName is durable. The draft has only the volatile part.
  2. func is a bare name under ex:. Same god-node problem as the static side; two functions named run in different modules collapse.
  3. No iteration ordinal. The two While events differ only by list position, so every query becomes a list traversal. Same fix as section 11: materialize an index.
  4. locals is a snapshot, not a derivation. Diffing adjacent events infers change, but there is no prov:wasDerivedFrom. Trace size is O(lines x locals).
  5. Values are captured as literals. A local holding a ModulusOfElasticity should serialize as that typed node, not as repr(). This is where the trace layer and the collapse of section 9 should meet and currently do not. It is the highest-value fix, because it is what makes a trace semantic rather than a log.
  6. Parallel vocabulary. awl:WorkflowRun, awl:HasStep, awl:calls and awl:Parameters are minted where prov:Activity, prov:used, p-plan:correspondsToStep and the WRROC CreateAction shape exist.
  7. os: {cores: 8} repeats on every event. Static environment belongs once on the run.

17. Instrumentation mechanics¶

The existing test implementation¶

osw-chatbot/src/osw_chatbot/tests/ast_.py (78 lines, 2025-03-27) is a working trace-to-AST mapping. test2.py beside it is its predecessor, capturing f_locals to YAML with no AST mapping.

A trace event exposes only f_lineno, never a column, so it packs both into the line number before compiling:

n.lineno = n.lineno * 1000 + n.col_offset
code = compile(a, '', 'exec')

That buys expression-level resolution. Verified on b = a + 2:

raw f_lineno decoded AST node
3004 line 3, col 4 a
3008 line 3, col 8 2
3004 line 3, col 4 BinOp a + 2
3000 line 3, col 0 Assign

One bug, confirmed by running it. The decode reuses the divided value:

line_no = frame.f_lineno
line_no = line_no // 1000       # line_no overwritten
col_offset = line_no % 1000     # modulo of the already-divided value

so col_offset always equals line_no. Keep the raw value instead:

raw = frame.f_lineno
line_no, col_offset = raw // 1000, raw % 1000

The file's closing comment also records a real finding worth preserving: coverage.py was evaluated and rejected because CoverageData does not store the called lines in order.

The hack is obsolete on Python 3.11¶

PEP 657 added co_positions() in 3.11. Setting frame.f_trace_opcodes = True and indexing co_positions() at f_lasti // 2 reproduces the same sub-expression sequence on unmodified source. Verified on b = a + 2:

('opcode', (1, 1, 4, 5))    -> a
('opcode', (1, 1, 8, 9))    -> 2
('opcode', (1, 1, 4, 9))    -> a + 2
('opcode', (1, 1, 0, 1))    -> b
lineno packing co_positions()
Requires AST rewrite and recompile Yes No
Works on installed third-party code No Yes
Column cap 999 None
End position No Yes, full (lineno, end_lineno, col, end_col) span

The third-party row is the unlock: the packing trick only ever sees code compiled by the tracer itself, which is why library internals were invisible. The end span matters too, because a full span maps onto an AST node exactly where a start offset alone is ambiguous.

C functions are visible¶

settrace does not see them. sys.setprofile does, and yields the fully qualified name directly as arg.__module__ + "." + arg.__qualname__:

('c_call', 'numpy',    'array')
('c_call', 'math',     'sqrt')
('c_call', 'builtins', 'len')

Both hooks can be active simultaneously, which attributes a C call to an AST node. Verified:

('AST', 3, 4)                    <- Call node math.sqrt(2)
('C-CALL', 'math.sqrt')          <- attributed here
('AST', 4, 4)
('C-CALL', 'builtins.len')

Limits: arg is the function object, so no arguments, and no position of its own. The position comes entirely from the interleaved trace event.

This is the runtime counterpart to section 8's retroactive mint: setprofile names the opaque callee, and semantics can be attached to that name later.

Three instrumentation strategies¶

Strategy Granularity Overhead Blind to
settrace plus opcode positions Expression High C functions
setprofile Call, including C Medium Positions, arguments
Decorator (Prefect, AiiDA, jobflow) Task boundary Negligible Everything undecorated

They compose rather than compete. Prefect is the pure decorator case: it never inspects code and records only what is decorated, so the DAG is discovered at runtime and nothing undecorated exists. Prefect 3's prefect.telemetry.run_telemetry emits a span per run with run metadata as attributes, state changes as events and traceparent propagated via run labels, but task input and output values are not span attributes, so there is no data lineage by default.

sys.monitoring (PEP 669), and what it costs¶

Loss versus settrace Detail
No frame object Every callback is (code, instruction_offset, ...). No frame, no documented route to locals. sys._getframe() works but negates the performance gain. This directly blocks the draft's locals capture
No columns on LINE LINE is func(code, line_number) alone; only other events carry instruction_offset, so co_positions() cannot be reached from LINE
Per-interpreter, not per-thread Stated in the PEP as a difference from settrace
Python 3.12+ Hard floor
Expensive reconfiguration set_events mid-run triggers de-optimization, "possibly taking hundreds of milliseconds"
Memory per code object ~40% for LINE with one tool, ~80% for INSTRUCTION, ~120% and ~200% with two or more
Six tool IDs 0 to 5, conventionally 0 debugger, 1 coverage, 2 profiler, 5 optimizer

Gains that matter here: a BRANCH event carrying destination_offset, which records the taken path directly instead of by diffing line events; a unified CALL event with signature (code, instruction_offset, callable, arg0) covering Python and C callables and supplying the first argument, which is strictly more than setprofile gives; per-event opt-in so LINE can be skipped entirely; and coexistence with settrace and setprofile, which behave "as if they were tools 6 and 7".

Conclusion: adopt sys.monitoring for BRANCH and CALL, not as a settrace replacement. Keep settrace alongside for the frame access that locals capture requires. The PEP explicitly supports running both.

Part V: Visual editing¶

A third consumer of the same document: a graph editor that renders and edits workflows and writes them back as Python. This part asks how compact the representation can get, what fidelity survives the round trip, and which libraries fit.

18. Compact representation¶

Measured on example A, round-trip verified identical to source.

Form Bytes % of raw
ast2json raw 4386 100%
Current awl, positions and ctx stripped 1689 39%
Compact form 1056 24%
The Python source itself 242 6%

The compact encoding is four rules:

_type       ->  _
Constant    ->  {"c": value}
Name        ->  {"$": id}
drop ctx, all position fields, None values, and empty lists

Compactness is a property of the encoder and decoder pair, not of the document. Dropping empty lists alone fails: Module.type_ignores is required, so unparse raises AttributeError. The decoder must rebuild every required field from cls._fields, exactly as unparse() in src/awl/core.py already re-adds lineno: 0. There is no compact form that survives a naive decoder.

Residual bloat against source is 4.4x, almost entirely {"_": ...} type tags and the arguments, arg, alias and keyword wrapper nodes. Those are precisely the transparent wrappers of section 7, and collapsing keyword into a dict on the Call is the existing slim notation generalised.

The editor encoding and the cutoff design are the same problem. The transparent and opaque type sets defined for the projection also define the compact form. Do not solve them twice.

19. Round-trip fidelity and write-back¶

ast.unparse discards trivia¶

ast.parse has no comment node at all, so every comment and all formatting is lost:

def procedure(cycles: int) -> None:
    # ramp to 4.2 V, CC phase only                     <- gone
    while i < cycles:
        charge(ChargeParam(target_voltage=4.2,   # cell limit per datasheet   <- gone
                           c_rate=0.23))              <- reflowed to one line

For workflows authored in the editor this is irrelevant. For editing a laboratory's existing procedure files it is fatal, and that is the audience the retrofit path of section 9 targets. It is also the practical face of tension 1: "the AST is the document and it round-trips" is true only modulo trivia, and a visual editor is where users notice.

CST, and why the choice is not a fork¶

A Concrete Syntax Tree keeps everything the parser saw.

AST (ast) CST (parso, libcst, tree-sitter)
Comments No node type exists Preserved
Whitespace and indentation Discarded Preserved
Redundant parentheses (a + b) identical to a + b Distinct
Quote style Both Constant('x') Distinct
Round-trip Lossy Byte-identical (verified: parso.parse(src).get_code() == src)

You do not have to choose between the compact form and trivia preservation. Keep the compact AST JSON as the editor model, never serialize a CST, and write edits back by source span. Verified with asttokens, already installed: locate the target_voltage value node, ask for its span (145, 148), splice the new literal into the original text. Both comments survive and layout is untouched.

The span machinery already exists in the design: section 17 needs co_positions() spans to attribute trace events, and the same tuples identify the patch target. One mechanism, two consumers. It also needs no unparser, only spans plus original text, so it works identically for tree-sitter, which removes the round-trip objection to a tree-sitter frontend raised in section 4.

Where spans stop and libcst starts¶

Span splicing has no opinion about which comment belongs to which statement, so reordering or reparenting a node cannot carry its trivia. libcst attaches trivia to named slots (leading_lines, trailing_whitespace) and handles it. Verified with libcst 1.9.0:

  • parse_module(src).code == src byte-identical.
  • A new statement can be constructed carrying modeled comments, leading and trailing, and emitted into source.
  • Inserting that statement into a while body leaves every original comment and the original odd spacing untouched.
  • Comments extract back into the model: leading comments attach to the following statement, trailing to the same line.

So a comment field in the editor is not a workaround, it is the right design. Modeled comments round-trip in both directions. Two limits found, both model decisions rather than bugs:

  • A comment inside call arguments attaches to an inner expression node, not to the statement. A per-step comment field captures statement-level comments only; expression-level trivia is preserved but not editable.
  • A section banner and a commented-out line arrive identically as leading comments. Attachment is positional, so do not try to classify them; keep an ordered list per step.

The resulting rule¶

Operation Fidelity
Edit a literal or parameter Lossless via asttokens spans, no new dependency
Add, delete or reorder steps Lossless via libcst
Regenerate a whole file from the graph Lossy by construction, and say so

20. Editor architecture¶

Paradigm before library¶

Node-graph editors model dataflow; block editors model control flow. AWL-LD's differentiator against CWL, PWD and semantikon is that it carries if and while. React Flow makes a nested loop body awkward, needing group nodes or subflow conventions; Blockly represents nested statements natively with C-shaped blocks and already ships a Python generator. Choosing a node-graph canvas quietly pushes the model back toward the dataflow shape section 2.5 says the ecosystem already occupies.

This is a product decision, and it is the same decision as whether control flow is the differentiator.

The decisive argument is a principle argument. RJSF's uiSchema is a second artifact. OO-LD exists because keeping structure and semantics in two files makes them drift; a separate uiSchema reintroduces exactly that drift for the presentation layer. jedison's x-format lives in the schema, the same in-schema extension pattern as x-oold-*, and applyOverlay supports the layered approach when it is wanted deliberately. Fair caveat: a uiSchema can be derived from x-oold-* at load time in about thirty lines, so this is a soft violation, but that mapping is a layer to own forever.

Two supporting points. This project is already on that codebase: OoldEditor imports @json-editor/json-editor and the AWL playground loads it too, and across two accounts jedison's author has 601 commits on json-editor against the original author's 315. So jedison is a migration and RJSF is a rewrite. And zero dependencies matters for the JupyterLite target that the HITL example explicitly names.

RJSF wins on React Flow embedding, since jedison is imperative DOM and needs a mount and unmount wrapper that survives React 18 StrictMode double-invocation; on bus factor, mitigated by MIT plus zero dependencies making vendoring trivial; and on TypeScript types.

The form library should follow the canvas decision. Blockly means no React, so jedison outright. React Flow makes RJSF the path of least resistance, though the jedison wrapper is still cheaper than a permanent uiSchema mapping.

Not yet verified: that @context and x-oold-* pass through jedison untouched. Both specifications require unknown keywords to be ignored and json-editor already handles these schemas, so the risk is low, but it deserves a test against a real OO-LD schema.

Unparsing to Python is not new: Blockly generates Python, BlockPy does dual block and text editing for Python, Pencil Code is bidirectional, App Inventor has an ANTLR-based blocks-to-text converter, and JetBrains MPS is the deep precedent for projecting one AST into several notations.

Part VI: Conclusions¶

21. What is genuinely novel¶

Narrowed against the survey, and narrower than an unexamined pitch would claim.

  1. AST-subtree collapse driven by a type-scoped context selected by the resolved callee. FnO reaches the same target from a different direction and semantikon is a live implementation of types-carry-semantics. What is unprecedented is only the mechanism: those attach semantics to a declared signature, whereas AWL rewrites a call site's AST subtree using the resolved callee's context. Claim the mechanism, not the goal.
  2. Progressive enhancement with no cliff. Every alternative is all-or-nothing per function (semantikon) or requires restructuring into a dataflow graph (PWD, CWL). AWL degrades continuously from plain code to fully typed. This is the strongest claim and the least obvious.
  3. Typed-boundary provenance at many points inside one function, rather than one annotation per signature, plus dimensional derivation of result types for arithmetic over typed quantities.
  4. One artifact serving three roles: round-trippable source document, semantic graph serialization, and visual editor model. srcML has the first; every code-to-RDF project has the second; Blockly and BlockPy have a form of the third but only over code authored in their own tool. Section 20 adds the part with no precedent at all: the editor palette is derived from the OO-LD schema, where every surveyed editor requires a hand-written block or node definition per construct.
  5. JSON Schema as whitelist of legal constructs and callees. CWL's requirements governs runtime capability; RO-Crate's conformsTo has the shape but no teeth. It is also the only sound answer to import *.
  6. Retroactive semantics via stable global identity: register the typed instantiation of an opaque callee once, and every prior reference gains meaning. Kythe's append-only entry model is the architectural precedent; nobody applies it to workflow semantics.
  7. RDF vocabulary for control flow in a workflow plan. Cautions: the ecosystem concluded imperative control flow is the wrong abstraction for a plan, so keep it in the source-fidelity layer and let the plan projection be dataflow; and BPMN-derived ontologies are the unsurveyed place to look.
  8. Recording which branch was taken and which iteration ran, as first-class trace data. Section 15 shows this exists nowhere: static languages omit branching, orchestrators expand it away at runtime, and AiiDA has real control flow but keeps branch and iteration logic out of its provenance graph. The draft in section 16 already does it. This is the retrospective counterpart to claim 7 and is at least as defensible.
  9. Expression-level trace-to-AST attribution, including opaque C callees. Section 17 shows the mechanism works today: opcode positions place each event on an AST node, and an interleaved setprofile names C functions the static analysis cannot see. No surveyed system attributes runtime events below the task boundary.

22. Prioritised recommendations¶

Priority Action Buys Costs
1 Neutral node vocabulary modelled on CPG, with PARSER_TYPE_NAME-style label preservation Language-agnostic graph without losing Python round-trip; unblocks any second frontend Vocabulary redesign, expensive to change later
2 Identity: FQN plus language, optional version, minted declaratively, with alias and alias-root pairs, and typed instantiation as the unit for callees Correct collapse, no ghost nodes, retroactive semantics Needs an import-resolution pass
3 Observation before inference: collect import and declaration facts, resolve separately Makes 2 auditable and re-runnable Refactor of core.py
4 Context lever: @list plus materialized index, embedded @vocab, explicit numeric typing, type-scoped disambiguation Fixes ordering, makes collapse lossless, closes the cross-language numeric hazard Cheapest item here
5 Reuse rather than rebuild: SCIP or Graphify for the type skeleton, Joern REACHING_DEF or python-graphs for dataflow Removes the largest build item from scope Integration and a CPG-to-RDF projection
6 Typed-boundary provenance, with the .pint.magnitude case as acceptance test The claim in 18.3 Requires 2, 3 and 5
7 FnO, P-Plan and PROV-O alignment Interoperability; avoids minting predicates that later need migrating Vocabulary mapping
8 Provenance via named graphs Declared and retrofitted meaning stay distinguishable Changes to_jsonld() to quads
9 Ambient-vocabulary filters, re-derived for workflows Removes god-nodes Lists built from scratch, not copied
10 Profile split Cutoff becomes a parameter Depends on 1 and 3

Items 1 and 2 come first: both are hard to change later, and both are prerequisites for a second frontend and for retroactive semantics.
